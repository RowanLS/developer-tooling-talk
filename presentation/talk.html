Main point:

Formatter: decides how code should look.

Linter: analyses code for suspicious constructs, style violations and some likely bugs.

Ruff does both, but they are conceptually different jobs.

Important:

Lint passing does NOT mean the program is correct. We’re gradually building different layers of checks.

Linters can catch real bugs too

def add_exclusion(
    participant: str,
    exclusions: list[str] = [],
) -> list[str]:
    exclusions.append(participant)
    return exclusions
add_exclusion("P01")  # ["P01"]
add_exclusion("P02")  # ["P01", "P02"]
B006 Do not use mutable data structures for argument defaults

Fix: create a new list for each call

def add_exclusion(
    participant: str,
    exclusions: list[str] | None = None,
) -> list[str]:
    if exclusions is None:
        exclusions = []

    exclusions.append(participant)
    return exclusions

A linter can catch code that is valid Python, but has surprising behaviour.

Main point

The previous Ruff examples were deliberately mundane: formatting, imports, and simple style problems. Ruff can also identify patterns associated with genuine bugs.

Explain the bug

  • Default argument expressions are evaluated when the function is defined, not each time it is called.
  • There is therefore one list shared between calls.
  • The first call mutates that list by adding P01.
  • The second call receives the same list, so P01 is unexpectedly still there.
  • Nothing crashes. That is what makes this kind of bug particularly unpleasant.

Ruff’s flake8-bugbear B006 rule detects mutable objects used as argument defaults.

Explain the fix

  • Use None as the default.
  • Create the empty list inside the function.
  • That expression is evaluated on each call, so each call gets its own list.
  • We still allow a caller to explicitly supply an existing list if that is what they intend.

Don’t live-code this example. It demonstrates the range of problems a linter can detect.

Connection to previous slide

Formatting and unused imports remove boring work from humans. But linting isn’t only cosmetic: some rules encode knowledge about Python constructs that are legal but commonly erroneous.

Transition: Once we’ve written down those assumptions, Pyright can compare different parts of the program and tell us when they disagree.

Types catch invalid choices before you run the code

from typing import Literal

def summarise(
    data: pd.DataFrame,
    method: Literal["mean", "median"],
):
    ...
summarise(data, method="mode")
                         ┌── not an allowed value
"mode" ───────────────✗

Expected "mean" or "median"
summarise(data, method="mean")  # ✓

Types can encode which values make sense, not just whether something is a string.

Main point This is more interesting than simply checking whether something is a string.

The function accepts a method, but not every possible string is meaningful. For this analysis, there are exactly two supported choices: mean and median.

Literal["mean", "median"] lets us express that as part of the function’s interface.

If another part of the program says:

summarise(data, method="mode")

that is perfectly valid Python and "mode" is correctly a string.

But it isn’t a value this function supports.

Pyright can identify that disagreement without executing the analysis.

Why care?

In a small example the mistake is obvious because the caller and function definition are on the same slide.

In a real project:

  • the function may be in another module;
  • the caller may have been written months later;
  • several people may be using the interface;
  • a typo may only occur on a rarely executed path.

The annotation also helps the editor: when calling this function, the editor can offer mean and median as the valid choices.

Important distinction

This still isn’t domain validation in the broader sense.

The type checker knows these values are allowed because we explicitly told it so. Later we’ll look at values such as negative reaction times where validity depends on scientific/domain knowledge.

Main point: Complexity usually accumulates gradually rather than because someone decided to write bad code.

C901 here is Ruff’s McCabe/cyclomatic complexity check.

Very roughly: each additional independent branch increases the number of possible paths through the function.

The exact threshold is not a law of nature. For this demo I deliberately use a strict threshold so the problem is visible.

Complexity metrics are signals for investigation, not proof that code is bad.

Notice: Pyright passes. The interfaces are type-consistent. Ruff’s complexity check is answering a different question.

Main point: Type correctness and domain validity are different things.

-250.0 is a perfectly valid float. Python accepts it. Pyright accepts it. Ruff has no reason to object.

But our domain knowledge says a reaction time cannot be negative.

A type checker answers: “What kind of value is this?”

Domain validation answers: “Is this value meaningful/allowed in this problem?”

Don’t claim pytest somehow knows scientific truth. We have to encode the relevant scientific/domain assumptions ourselves.

demo-next → 05-tests.

Main point: Neither Python nor Pyright knows what a scientifically valid reaction time is. We have to encode that domain knowledge ourselves.

There are three steps here:

  1. State the domain rule in the application. We know a reaction time cannot be negative, so validate_data() rejects values <= 0.

    This is validation, not testing. Its job is to stop the analysis rather than silently process impossible input.

  2. Turn the expected behaviour into a test. The test constructs a small synthetic dataset containing -250 ms and says:

    When this data is validated, I expect a ValueError.

    The -250 value is synthetic test data. We are not introducing an error into the real dataset.

  3. Run the expectation automatically.

    uv run pytest

    pytest checks that the application still behaves as we specified.

Why test something we’ve just implemented? Because the test preserves that expectation when the code changes later. If somebody refactors validate_data() and accidentally removes the check, the test should fail.

Important distinction: pytest does not know that negative reaction times are impossible. The domain knowledge comes from us. pytest gives us a repeatable way to check that the software continues to implement that knowledge.

Research-practice point: Raw data should remain immutable. If real observations fail validation, investigate their provenance. Any justified correction or exclusion should happen through an explicit, documented processing step rather than silently editing the source data.

Key line: We’ve moved another assumption from something I know to something the project can check.

Transition: And this is why we need several tools rather than one universal “quality checker”: they know about different kinds of mistakes.

There isn’t one “code quality” tool. They answer different questions.

Main point: These tools are complementary, not competing alternatives.

Ruff: mostly source-level/static quality checks.

Pyright: consistency of typed interfaces.

Complexity: a maintainability signal.

pytest: behaviour we have explicitly specified.

Important qualification: pytest only catches behaviour represented by tests. A green test suite does NOT prove the program is correct.

Each tool reduces a particular class of risk.

CI = continuous integration.

At the previous stage, pre-commit stopped me locally. But local hooks can be bypassed with –no-verify, or someone may never install them. So I deliberately bypassed the hook and pushed the same regression to this PR. Ruff passes. Pyright passes. pytest fails. The important difference is that this check is now being run by the shared repository, not by my development environment. If we make CI a required check, this PR cannot be merged until the problem is fixed.

Why this matters:

  • independent of whether I remembered;
  • independent of my editor;
  • independent of my local hooks;
  • gives collaborators one shared result.

CI doesn’t magically make tests better. It makes running the agreed checks consistent and visible.

Pre-commit: fast local feedback. CI: independent shared verification.

Dependabot does not mean “automatically trust every new dependency version”.

It automates discovery/proposal of updates.

The useful workflow is:

update proposed → CI runs → tests/checks pass or fail → human reviews → merge or reject

This is why dependency automation becomes much more useful after tests and CI already exist.

Maintenance is part of software development, not something that only happens while initially writing the code.

demo-next -> 09-final. Run make check, then make figure.

  • Make is not replacing Ruff, Pyright or pytest. It gives common project workflows stable, memorable names.
  • make check means “run the checks this project considers important”; users don’t need to remember every underlying command.
  • This gives the project a small interface or vocabulary: make check, make figure.
  • The commands underneath can change later without changing the documented workflow for users.
  • This is useful for collaborators, CI, documentation, and future me.
  • Make can do considerably more with dependencies between files and targets; here I’m deliberately using it mostly as a simple task runner.

Closing message The common theme across most of these tools is feedback latency.

Walk down the diagram:

  • Ruff or Pyright tells me something while I’m still writing the code.
  • Tests tell me behaviour has changed before I commit it.
  • Pre-commit catches problems before the change enters history.
  • CI catches them when the project reaches the shared repository.
  • Without those layers, the first person to notice may be a collaborator, a user, or—worst of all—someone looking at a published result.

The earlier a problem is found:

  • the relevant code is more likely still to be in my head;
  • fewer people depend on the broken behaviour;
  • there is less history to investigate;
  • fixing it is generally less disruptive.

But don’t overclaim

This isn’t a claim that every bug becomes literally more expensive by some fixed amount at every stage.

The principle is simply that short feedback loops are usually easier to work with.

There is a second theme as well: hidden knowledge.

Across the talk we moved knowledge out of my head and into the project:

  • dependencies → pyproject.toml / uv.lock
  • interfaces → type annotations
  • domain expectations → tests
  • quality expectations → configuration
  • checks → pre-commit and CI
  • common workflows → Makefile

That is what I mean by making software more professional: not making it complicated for its own sake, but making important assumptions explicit and checkable.
